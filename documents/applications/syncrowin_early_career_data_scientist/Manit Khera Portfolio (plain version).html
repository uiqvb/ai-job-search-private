Smart Clothesline Robot

Embedded Systems unit · 93
Arduino C++ · Raspberry Pi · Python/Flask · MQTT Demo video Write-up Code

The problem The robot moves washing between a sunny spot and a sheltered spot by following a tape line. An Arduino reads six sensors and sends the readings every five seconds over MQTT to a Python program I wrote on a Raspberry Pi, which decides what to do.

What I did The rain sensor was cheap and not very reliable, so the robot also checks the weather forecast before it moves. I tested this by wetting the sensor, and by feeding it fake rain readings to make sure it would go with the forecast.

The harder problem was power. On fresh batteries everything worked, but once they dropped to around 90 percent the robot started resetting at random. I assumed the batteries were the problem and kept buying new ones, probably about $100 worth, before I went back through the logs. The boot ID and reset cause in each message showed the board was browning out, which led me to a faulty voltage converter.

What I learned I should have looked at the logs much earlier. I now add fields like those to everything I build, because they are what made the fault findable. I also still have a pile of batteries sitting at about 90 percent.

Robot Controller API

Backend Development unit · 100/100 · shown at Deakin Open Day
.NET 8 · C# · PostgreSQL · Docker · Jenkins Open Day demo Code

The problem For my backend unit I wrote an API that does the robot's thinking. The robot just asks the server what to do next. When I connected it to the clothesline robot, the server and the robot often disagreed about where the robot actually was.

What I did I started logging every command and result to a history table in PostgreSQL, so I could see what had really happened. I also planned for the Wi-Fi dropping out, even though it never did. Each command comes with instructions for undoing it, so if the robot hears nothing for seven seconds it backs up along its last moves and then reports what it did. The server runs that report through a simulation before saving it.

How it went When I tested it on the real robot, it stopped exactly where the server predicted. The project got 100/100 and was picked for Deakin Open Day, where I demoed it to prospective students and their parents.

Scaling a Robot Dispatch API

Distributed Programming unit
C# · ASP.NET Core · PostgreSQL · Azure · NBomber · xUnit Demo video Code Report

The problem For a third unit I wanted to see what would happen with far more robots. I simulated a fleet on Azure and ran it against my backend. At 5,000 robots it didn't finish a single job.

What I did I went through the code and found 12 problems, including a race where two robots could claim the same job. I made job claims atomic in PostgreSQL, added a limit so the server tells robots to retry instead of falling over, and added a second server. Then I ran 80 benchmark runs on Azure, repeating each grid setup three times and taking the median so one lucky run couldn't skew the result.

What I learned At 400 robots the median time to claim a job went from 766.5 ms to 59.5 ms, with 54 automated tests behind the changes. I never found the new limit, because my load generator ran out of capacity before the backend did. I wrote the method and results up in a report.
